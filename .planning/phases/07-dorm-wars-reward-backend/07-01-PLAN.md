<hazards>
- **Snapshot CREATE TABLE fails because column type mismatches live** → STOP. Re-fetch OpenAPI schema, compare column-by-column with Decision #5 DDL, update the migration before re-applying. Do NOT drop and recreate.
- **`CREATE POLICY IF NOT EXISTS` syntax error** → Supabase runs PG15+, but if the apply fails, wrap each `CREATE POLICY` in `DO $$ BEGIN ... EXCEPTION WHEN duplicate_object THEN NULL; END $$;` per RESEARCH note at line 930.
- **`apply_migration` reports the migration name as already applied** → check `supabase_migrations.schema_migrations` table. If a stale row exists, do NOT delete it — instead bump the migration timestamp by one second (e.g., `20260516010000_*`) and retry.
- **Row counts change after apply** → STOP and investigate. The snapshot must be a no-op. A delta means a CHECK constraint failed silently or a column default backfilled wrong. Roll back is via the Supabase point-in-time recovery; do not attempt a corrective migration without product approval.
- **`ADD COLUMN IF NOT EXISTS` succeeds but column appears missing** → some PG versions need `NOT VALID` on the constraint; Decision #6 uses `NOT NULL DEFAULT 0` which rewrites the table. If the table is huge (`subscriptions` is not), this could lock. Run `EXPLAIN` first if unsure.
</hazards>
