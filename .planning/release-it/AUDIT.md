# Release It! Audit — Raw Findings
> Source: 13-agent workflow `wf_1494cc14-2e4` (2026-06-21). Evidence companion to PLAN.md.

**System overall: 6.1/10**

System by dimension: antiPatterns 6, stabilityPatterns 6.5, capacity 6, deployment 6, observability 5.5, chaos 6.5

## Cross-cutting risks

### [CRITICAL] The timeout-wrapped Supabase admin client exists but is bypassed by raw clients on the highest-traffic surfaces
- **Dimension:** Stability Anti-Patterns / Timeouts (systemic)
- **Areas:** Marketing site + Auth/Onboarding, User Dashboard, Dorm Wars, Payments / Checkout, Scheduled Jobs / Cron, WhatsApp Messaging, AI Chatbot & Support
- **Impact:** createAdminSupabaseClient() (15s AbortController) is the codebase's own correct primitive, yet raw createClient()/createAdminClient() is used in onboarding/actions.ts, r/[cid]/actions.ts, both /api/whatsapp routes, /api/referral/inviter, all four dorm-wars API routes, support-chat, checkout, and 4 of 5 /api/internal routes. The user-scoped server client (utils/supabase/server.ts, behind every authenticated dashboard read) also has no timeout. This is one bug repeated ~15 times. When Ohio Supabase or PgBouncer browns out, every one of these paths hangs to the Netlify wall-clock instead of failing fast, exhausting function concurrency simultaneously across acquisition, dashboard, payments, gamification, and cron — a single DB slowdown becomes a whole-platform brownout. Highest-leverage system fix in the audit.

### [CRITICAL] Zero circuit breakers anywhere; a single down vendor is retried on every request and every cron tick
- **Dimension:** Stability Patterns / Bulkheads + Circuit Breakers (absent)
- **Areas:** Payments / Checkout, WhatsApp Messaging, AI Chatbot & Support, Scheduled Jobs / Cron, Platform: Email/Zoho, Staff / Intern Program, Delivery Rider / Ops Panel
- **Impact:** grep confirms no circuit/breaker/opossum in infra. Per-call timeouts exist on most vendor paths but there is no shared open-circuit state, so during a multi-hour Meta/Zoho/ZeptoMail/Stripe/Gemini outage every request and every retry-cron tick pays the full timeout cost against a dead endpoint, amplifying load exactly when the dependency is weakest. Worse, the admin-alert channel (send_admin_whatsapp_alert) itself rides Meta, so a Meta outage also silences the alert that would warn of it — a self-blinding failure mode. The retry crons (hourly post-payment, /5min dispatch) re-flood down vendors with no backoff escalation or shedding.

### [CRITICAL] Three unauthenticated, unmetered, money-spending endpoints with no shared rate limiter
- **Dimension:** Stability Anti-Patterns / Self-Denial-of-Wallet (cross-feature)
- **Areas:** AI Chatbot & Support, Marketing site + Auth/Onboarding, Staff / Intern Program, WhatsApp Messaging
- **Impact:** No rate-limit infrastructure exists anywhere (grep: none in infra/shared). /api/chat is fully anonymous and bills Gemini tokens (30 msgs x 4000 chars/req); /api/whatsapp/start is throttled per-phone only, so phone rotation drains paid WhatsApp template credits and burns Meta quota (blocking real OTPs); verifyStaffClaim has no lockout on claim-code brute force. Each abuse path is also a service-role DB load generator. The referral and Dorm Wars features are explicitly designed for virality — a successful viral spike or a scripted abuser both translate directly into unbounded third-party spend AND function-concurrency exhaustion that starves paid/auth flows. A shared limiter is missing precisely where money leaves the building.

### [HIGH] WhatsApp is a hard, single-channel gate on ALL new-customer acquisition with no degraded path
- **Dimension:** Adaptation & Chaos / Single-channel acquisition gate
- **Areas:** Marketing site + Auth/Onboarding, WhatsApp Messaging, Staff / Intern Program
- **Impact:** Onboarding, referral claim, and staff claim all hard-require a verified WhatsApp OTP with no SMS/email fallback. Meta WhatsApp template rejection/rename is a documented recurring failure mode in this codebase (the v-series migrations and a real 5-day silent regression). When Meta is down or a template goes into review, 100% of new acquisition stops end-to-end with no automated degradation — recovery requires Meta to recover or a code deploy. The entire top of the revenue funnel has a single point of failure on a third party with a known history of breaking.

### [HIGH] Repeated full-table customers/subscriptions scans on hot and admin paths that grow with the customer base
- **Dimension:** Capacity & Availability / Unbounded full-table scans (systemic pattern)
- **Areas:** Admin Panel, Delivery Rider / Ops Panel, Kitchen Team Panel, Dorm Wars, User Dashboard
- **Impact:** The same anti-pattern recurs independently: admin list pages SELECT the entire customers table per load; getDormCounts + the delivery-confirmed fanout scan all customers + all live subscriptions in-memory on every rider page load, every WhatsApp inbound, and the 8PM failsafe; kitchen getKitchenCounts pulls full customers+subscriptions every 60s per open tab; dorm-wars admin loads the whole customers table; dashboard history has no LIMIT. Harmless at today's ~32 customers but every one degrades linearly with growth, and they all hit the same Supabase connection pool. A growth or marketing spike pressures the shared pool from multiple directions at once with no pagination anywhere.

### [HIGH] Money/trust-critical paths are observability dark — admin, kitchen, ops, dorm-wars, staff, AI have no Sentry/pino
- **Dimension:** Health Checks & Observability (systemic blind spots)
- **Areas:** Admin Panel, Kitchen Team Panel, Delivery Rider / Ops Panel, Staff / Intern Program, Dorm Wars, AI Chatbot & Support, Scheduled Jobs / Cron
- **Impact:** pino + Sentry are wired and used well in payments/whatsapp/platform, but six areas running the highest-blast-radius operations (refunds, credit issuance, pricing changes, kitchen counts, delivery chain-of-custody, AI cost) use bare console.error with no alerting, metrics, or trace correlation. Combined with several silent-failure designs (kitchen counts coalesce DB errors to a believable 0/0; delivery marked verified even when customer notifications fail; cron health goes green the instant pg_net enqueues without confirming the internal route returned 2xx), mean-time-to-detect for a money or service-blanking incident is effectively 'a human notices' or 'a customer complains.' There is no symptom-based alerting layer spanning the system.

### [HIGH] Stripe SDK has no timeout, no retries, and no idempotency key on refunds — same gap in 3 areas
- **Dimension:** Stability Patterns / Stripe money path (repeated across areas)
- **Areas:** Payments / Checkout, Admin Panel, Staff / Intern Program
- **Impact:** Confirmed in src/infra/stripe/client.ts: new Stripe(key, {apiVersion}) only — inherits the SDK's 80s default timeout and 0 retries. A slow Stripe hangs checkout (no maxDuration -> dies at ~10s leaving an orphaned coupon + reserved credit) and admin/staff refund actions (up to ~80s spinner). refunds.create carries no idempotencyKey, so a refund that succeeds-then-times-out can be double-issued when an admin is told 'refund failed, settle manually' and does it again in the Stripe dashboard — real double money out. One client config + one idempotency key fixes all three areas at once.

### [MEDIUM] Inbound WhatsApp webhook does full fan-out inline before ACKing Meta, with two un-timed outbound fetches
- **Dimension:** Stability Anti-Patterns / Webhook ACK latency + un-timed fetches
- **Areas:** WhatsApp Messaging, Delivery Rider / Ops Panel, Platform: Email/Zoho
- **Impact:** whatsapp-inbound/route.ts awaits the entire processAsync chain + relayChatwoot (raw fetch, no timeout) before returning 200, and replyToRider is also a raw un-timed fetch (not even try/caught). A stalled Chatwoot or Meta Graph endpoint hangs the function to the wall-clock; Meta then re-delivers the webhook (slow ACK = retry), multiplying load during the exact upstream-latency condition. The route also lacks maxDuration, so large-dorm serial fanout can be truncated mid-loop, leaving some customers notified and others silently not.

### [MEDIUM] 131 scattered process.env reads with no fail-fast validation; pg_cron defined in drift-prone migrations; no feature flags
- **Dimension:** Deployment & Release / Config + migration drift + no rollback story
- **Areas:** Platform: Email/Zoho, Scheduled Jobs / Cron, Payments / Checkout, WhatsApp Messaging, Staff / Intern Program
- **Impact:** No centralized env schema: a deploy missing ZEPTOMAIL_TPL_*, ZOHO_REFRESH_TOKEN, or a WhatsApp secret builds green and fails customer-facing hours later. Crons live in SQL migrations that MEMORY.md and multiple areas flag as STALE vs the live DB (dedup logic, tick bodies, cron times have drifted), so the rollback/expand-contract story is untrustworthy — a redeploy could silently revert live hardening. Migrations are additive-only (no DROP/RENAME observed) which is backward-compatible, but the contract phase never happens and there is no canary/feature-flag/kill-switch anywhere on Netlify, so pausing a runaway feature (staff program, a bad pricing change, a viral abuse wave) requires a full build, not a config toggle.

## Per-area findings

### Marketing site + Auth/Onboarding (public funnel) — 5.8/10
`AP 5.5 · SP 5 · Cap 6 · Dep 6 · Obs 7.5 · Chaos 6`

The public funnel is impressively hardened on the security/abuse axis — HMAC single-use OTPs, layered referral fraud caps, open-redirect guards, and email-enumeration handling are all well done — but it is notably weak on Release It! resilience fundamentals. The single biggest gap: every Supabase admin call across onboarding, referral claim, and the WhatsApp/inviter endpoints uses the raw client with no timeout, even though a timeout-wrapped helper already exists in the codebase, so a slow DB under load can hang the highest-traffic serverless paths and cascade. Self-denial risk is real — WhatsApp OTP send is throttled per-phone only (trivially bypassed by phone rotation to drain paid credits) and the unauthenticated /api/referral/inviter leaks customer first names with no rate limit. There are no circuit breakers and no degraded path when Meta WhatsApp is down, which hard-stops all acquisition. Observability (pino + Sentry + admin alerts) is the strongest dimension and gives good incident visibility once something breaks.

**Top risks:**
- **[high]** (Stability Anti-Patterns / Timeouts) Every Supabase admin call in the public funnel has NO timeout
  - _evidence:_ src/app/onboarding/actions.ts:78,113; src/app/r/[cid]/actions.ts:234,261,769; src/app/api/whatsapp/start/route.ts:13; src/app/api/whatsapp/check/route.ts:8; src/app/api/referral/inviter/route.ts:12 all call raw createAdminClient() from @supabase/supabase-js. The timeout-wrapped helper createAdminSupabaseClient() (15s, src/infra/supabase/admin-client.ts:20-34) exists and is used elsewhere but is NOT used on any of these paths.
  - _impact:_ When Supabase (Ohio) is slow under load, the default PostgREST fetch has no read timeout, so every onboarding signup, every referral claim (which fires ~15 sequential queries), and the public /api/referral/inviter lookup can hang the Netlify function until the platform's 10-26s wall-clock kill. Functions pile up, concurrency exhausts, and the whole funnel browns out — the textbook integration-point-without-timeout cascading failure, on the highest-traffic surface.
- **[high]** (Stability Anti-Patterns / Self-Denial + Capacity) WhatsApp OTP send is rate-limited per-phone only — no IP/global cap; trivial credit-drain & PII enumeration
  - _evidence:_ src/app/api/whatsapp/start/route.ts: MAX_SENDS_PER_HOUR=5 keyed solely on .eq('phone', phone) (lines 33-40); no resolveClientIp() / x-forwarded-for cap (the referral flow has one at r/[cid]/actions.ts:520-534 but the OTP endpoint does not). /api/referral/inviter (src/app/api/referral/inviter/route.ts) is unauthenticated, unthrottled, service-role, and returns a real customer first name for any valid CID.
  - _impact:_ An abuser rotates phone numbers (each gets its own fresh 5/hr bucket) to force thousands of paid WhatsApp template sends — direct money loss and a self-inflicted DoS on Meta quota that blocks real customers' OTPs. Separately, the inviter endpoint lets anyone brute-force the small CID space to harvest customer first names + confirm which CIDs are real (enumeration), with no cost or rate limit.
- **[medium]** (Stability Anti-Patterns / Blocked serial awaits) claimGift performs ~15 sequential, unbounded, un-timed Supabase round-trips per request
  - _evidence:_ src/app/r/[cid]/actions.ts:286-757 — inviter lookup, getUser, phoneOtp, ownLiveSubs, phoneCustomer, phoneLiveSubs, phoneClaimed, emailClaimed, inviterCustomer, pairExists, two rate-limit counts, IP count, device match, two inserts, customers upsert, sub insert — mostly awaited serially, all on the no-timeout raw client.
  - _impact:_ Under a viral spike (the explicit design goal of the referral feature) each claim holds a function for the sum of ~15 DB latencies with no ceiling. Latency stacks, Supabase connection pool saturates, and slow claims tie up serverless concurrency — slow-response + self-denial combined exactly when traffic is highest.
- **[medium]** (Adaptation & Chaos / Graceful degradation) OTP send/verify hard-fail when Meta WhatsApp is down — no degraded path
  - _evidence:_ src/app/api/whatsapp/start/route.ts:69-74 returns 502 on sendOtpTemplate throw; src/infra/meta-whatsapp/client.ts has an 8s timeout (good) but no retry/backoff and no circuit breaker. There is no fallback channel (e.g. email OTP) when WhatsApp is unavailable.
  - _impact:_ If Meta WhatsApp Cloud API has an outage or the template goes into review/rejected state, NO new customer can onboard and NO referral can be claimed — phone verification is a hard gate (onboarding/actions.ts:105-108, r/[cid]/actions.ts:315-329). The entire acquisition funnel stops with no automated degradation; recovery requires Meta to recover or a manual code change.
- **[medium]** (Stability Patterns / Idempotency & no circuit breakers) No circuit breakers/bulkheads; multi-step writes are not transactional, relying on manual compensation
  - _evidence:_ claimGift rolls back by hand after partial failure (r/[cid]/actions.ts:593, 653-654) and emits notifyAdmin for the welcome-meal-sub gap (line 736) rather than a transaction; onboarding/actions.ts:204-212 leaves an auth user with no customers row and alerts an admin. No circuit breaker wraps Meta/Supabase, so a degraded dependency is retried on every request.
  - _impact:_ Partial-failure windows leave orphaned auth users / claimed-but-no-meal states that need human backfill (alerts fire, but a human must act). With no breaker, a flapping dependency gets hammered every request instead of failing fast, amplifying load during an incident.
- **[low]** (Capacity / Unbounded query) Lifetime-conversion count query is unbounded
  - _evidence:_ src/app/r/[cid]/actions.ts:834-838 counts all converted referrals for an inviter with no date bound (head:true count, so no row payload — but a full index scan). Most other queries correctly use .limit() / maybeSingle().
  - _impact:_ Low today; the cash-ladder count grows with a power-inviter's lifetime conversions. Acceptable for now but worth a ceiling — it is the one count in the hot path without an upper bound.

**Strengths:**
- OTP design is genuinely hardened: HMAC-keyed code hashes bound to phone (src/shared/otp-hash.ts), single-use via consumed_at consumed only after full success (onboarding/actions.ts:217, r/[cid]/actions.ts:669), atomic attempt-increment RPC to prevent concurrent brute-force (whatsapp/check/route.ts:28), and a 5-attempt cap.
- Open-redirect protection is consistent and correct: safeNext() regex on login/actions.ts:9-11, auth/confirm/route.ts:21-23, and middleware.ts:90 all reject absolute/protocol-relative next params.
- Strong anti-abuse on referral claims: lifetime phone+email dedupe with Gmail dot/+tag normalization (actions.ts:60-73), self-referral block, per-IP 24h hard cap (hashed, peppered), inviter weekly/open-gift caps, device-fp soft flags routed to a review queue, and a CAS guard on conversion to prevent double-credit (actions.ts:787-795).
- Email enumeration is handled thoughtfully: Supabase's obfuscated-existing-user response (empty identities array) is detected and bounced to /login instead of hanging on the OTP screen (onboarding/actions.ts:159-166); password reset never discloses whether an email exists (login/actions.ts:96-103).
- Observability is solid for an MVP: pino structured logging with credential redaction (infra/logging/logger.ts), Sentry wired across server/edge/client with onRequestError, user attribution via requireUser(), local-variable capture, and notifyAdmin WhatsApp alerts on every money/trust-critical failure path.
- Outbound Meta and the wrapped Supabase admin client both enforce timeouts (8s and 15s) via a shared fetchWithTimeout AbortController helper — the pattern exists and is correct; it just isn't applied to the funnel's raw admin clients.
- Middleware strips client-supplied x-user-* headers before trusting them (utils/supabase/middleware.ts:7-9), closing a header-spoofing privilege path.

**Improvements:**
- _(now · Stability Anti-Patterns)_ Replace every raw createAdminClient() call in onboarding/actions.ts, r/[cid]/actions.ts, and both /api/whatsapp routes + /api/referral/inviter with the timeout-wrapped createAdminSupabaseClient() from infra/supabase/admin-client.ts. This is a near-mechanical swap that gives the whole public funnel a 15s read ceiling for free.
- _(now · Self-Denial / Abuse)_ Add an IP-based cap to /api/whatsapp/start (reuse resolveClientIp()+hashIp() from the referral action) so phone-rotation can't drain paid WhatsApp credits, and add a small rate limit + (optionally) hashed-CID lookup to /api/referral/inviter to stop unauthenticated CID enumeration and customer-name harvesting.
- _(next · Adaptation & Chaos)_ Add a circuit breaker + a fallback path for WhatsApp OTP: when Meta send fails (502/timeout) repeatedly, fail fast and offer an email-OTP alternative so an upstream WhatsApp outage doesn't fully halt acquisition. Also add jittered single-retry for the idempotent Meta send.
- _(next · Capacity)_ Parallelize the independent read checks in claimGift (e.g. phoneClaimed / emailClaimed / pairExists / inviterCustomer / rate-limit counts) with Promise.all where there is no data dependency, to cut per-claim latency under viral load. Bound the lifetime-conversions count (actions.ts:834) or precompute it.
- _(next · Stability Patterns)_ Move the multi-write claim/onboarding sequences into a single Postgres RPC (transaction) so partial failures roll back atomically instead of via hand-coded compensating deletes + admin alerts, eliminating the orphaned-auth-user and claimed-but-no-meal states.
- _(later · Observability)_ Migrate the remaining console.log/console.error in the funnel actions to the pino logger so funnel failures get structured fields + Sentry forwarding, and add a deep health check (Supabase + Meta reachability) for symptom-based alerting rather than only post-hoc notifyAdmin.

### User Dashboard (desktop + mobile split) — 6.5/10
`AP 6.5 · SP 6 · Cap 7 · Dep 7.5 · Obs 6 · Chaos 7`

The authenticated dashboard's write path is the strongest part of this codebase: subscription mutations use compare-and-swap guards for idempotency, fail-fast validation, fire-and-forget notifications, and per-op Sentry metrics, and the menu catalog + static dish pages degrade gracefully under DB failure. The read path is the weak spot — the user-scoped Supabase client (behind every dashboard query) has no timeout, so a slow Ohio region can hang RSC renders until the Netlify function ceiling, and the Gemini support chat call has no abort/retry/circuit-breaker. Capacity is mostly bounded (per-user reads, React cache dedup, single fetch shared by mobile and desktop), but the plan-history query is unbounded and grows with tenure. Observability is present (Sentry wired via instrumentation) but caught read/AI errors are only console.error'd, so degraded dependencies surface as user complaints rather than alerts. Highest-leverage fixes: a timeout on the user Supabase client, a LIMIT on history, and an abortSignal on the Gemini call.

**Top risks:**
- **[high]** (Stability anti-patterns / Patterns (timeouts)) User-scoped Supabase client has no timeout — every authenticated dashboard read can hang
  - _evidence:_ src/utils/supabase/server.ts:4-26 (createServerClient with no global.fetch override / timeout), consumed by src/infra/supabase/subscriptions-repo.ts getCustomer/getActiveSubscription/getAllSubscriptions, history/page.tsx:45, profile/page.tsx:13, explore-plans/page.tsx getRedeemableCredit
  - _impact:_ Plain fetch has no per-call timeout. If the Ohio Supabase region is slow/stalled (we serve Dubai), every RSC render in /dashboard/* (home, plan, menu, history, profile) blocks on Promise.all of these reads until the Netlify function ceiling, tying up function concurrency and showing users a hung page instead of failing fast. The admin client already solves this (admin-client.ts:18-33 wraps fetchWithTimeout 15s); the user client does not.
- **[medium]** (Stability patterns (timeout / circuit breaker on external dep)) Gemini support-chat call has no timeout, retry, or circuit breaker

### Staff / Intern Program — 5.5/10

### Payments / Checkout / Stripe webhook — 6.4/10
`AP 6 · SP 7 · Cap 6 · Dep 6 · Obs 7 · Chaos 6`

This is a mature, security-conscious payments area with genuinely strong webhook idempotency (session checkpoint + resume mode + 23505 race rollback), fail-closed signature verification, robust pre-Stripe tamper validation, and a well-designed credit-reservation scheme that prevents double-spend across tabs. Resilience of downstream side-effects is partial: the three fan-out channels are nicely bulkheaded and retried, but credit-flip/referral/customer-patch failures inside a completed webhook are alert-and-human-reconcile only, and the retry cron lacks exponential backoff/jitter. **Top risks:**

  - _evidence:_ src/infra/stripe/client.ts:26 — new Stripe(key, { apiVersion }) only; no `timeout`, no `maxNetworkRetries`

Inside the checkout route (which has no maxDuration → Netlify's ~10s cap) a slow Stripe coupons.create or sessions.create silently dies at the function boundary, not at a controlled timeout, so the credit reservation is left in 'reserved' until the 24h lazy-release. Inside the webhook (maxDuration=60) a slow Stripe leg eats the budget. No automatic retry on transient 5xx/network blips means a single Stripe hiccup fails an otherwise-good checkout.
- **[high]** (Capacity & Availability) Checkout route runs ~8 serial Supabase round-trips + Stripe calls with no maxDuration

  - _evidence:_ src/contexts/payments/usecases/handle-stripe-event.ts:92-102 (dedup via orders.stripe_session_id + webhook_completed_at) and credit-flip/referral/customer-patch failures only console.error + notifyAdmin (lines 428, 591, 626); retry cron only re-runs the 3 fanout channels (supabase/migrations/20260525_post_payment_retry_cron.sql:92-94)

  - _evidence:_ src/contexts/payments/usecases/handle-stripe-event.ts:684 runPostPaymentFanout awaited; src/contexts/payments/usecases/post-payment-fanout.ts:74 Promise.all of whatsapp+email; ZeptoMail uses fetchWithTimeout (src/infra/zeptomail/client.ts:132) but the whole fanout is in the webhook's 60s budget

- **[medium]** (Stability Patterns / Retry) Retry cron has an attempt cap but no exponential backoff or jitter; fixed hourly cadence with LIMIT 50/tick
  - _evidence:_ supabase/migrations/20260525_post_payment_retry_cron.sql:95-96 (LIMIT 50, hourly '15 * * * *'), max_attempts>=5 stop (line 121); no per-attempt delay scaling

### Platform: Data layer, Email/Zoho, Health & Observability — 7/10
`AP 7.5 · SP 7 · Cap 7 · Dep 5.5 · Obs 8 · Chaos 7`

This platform layer is notably well-engineered for a serverless app: a real timeout layer (fetchWithTimeout/AbortController) wraps every documented integration point, the Stripe webhook fan-out has genuine per-channel idempotency markers and failure isolation, the slow Zoho pipeline is deferred off the hot path, and observability (pino with redaction + Sentry tracing/profiling/log-forwarding) is mature. The biggest gaps are the absence of any circuit breaker (retry crons will hammer a down vendor) and the lack of centralized fail-fast env-config validation across 131 scattered process.env reads, so a misconfigured deploy boots green and fails customer-facing. Smaller stability holes remain (two un-timed fetches in the WhatsApp-inbound webhook, no abort on AI streamText, Stripe SDK defaults) and the highest-value money paths still log via console.error without trace correlation. Live Supabase advisors confirm the RLS deny-all model is intact but ~25 functions have mutable search_path and a few SECURITY DEFINER functions are anon-executable. Overall a 7/10 — production-capable with strong fundamentals, held back from hardened by missing breakers, env-validation, and uniform structured logging.

**Top risks:**
- **[high]** (Stability anti-patterns / Adaptation) No circuit breaker on any external dependency — repeated retries hammer a down vendor
  - _evidence:_ grep for circuit/breaker/opossum across src returns only Dorm-Wars naming false-positives; infra/zoho/client.ts, infra/zeptomail/client.ts, infra/meta-whatsapp/client.ts all timeout-and-throw with no breaker. The hourly post-payment-retry cron (src/app/api/internal/post-payment-retry/route.ts) and the every-minute Zoho dispatch cron re-call dead vendors every cycle.
  - _impact:_ When Zoho or ZeptoMail is down/slow, every retry tick still pays the full 10-15s timeout per order and re-floods the failing vendor. With a backlog of unpaid invoices the per-minute cron fans out serial 70-90s Zoho pipelines against a dead endpoint, consuming function time and delaying recovery instead of backing off. No fast-fail once a dependency is known-bad.
- **[high]** (Deployment & Release) No centralized/fail-fast env config validation — 131 scattered process.env reads
  - _evidence:_ No env schema (no zod/@t3-oss/env hit); 131 `process.env` reads across src. Validation is ad-hoc and lazy: zeptomail/client.ts throws at module-load only for ZEPTOMAIL_REGION but checks ZEPTOMAIL_API_TOKEN/FROM_ADDRESS at send time; ZEPTOMAIL_TPL_* keys throw only when that specific email fires; Stripe key throws at call time. health route checks only SUPABASE_SERVICE_ROLE_KEY + 2 NEXT_PUBLIC vars.
  - _impact:_ A deploy missing e.g. ZEPTOMAIL_TPL_RENEW_NUDGE or ZOHO_REFRESH_TOKEN builds and boots green; the failure surfaces only when a customer pays or a cron fires hours later — caught customer-facing (post_payment_errors + admin WhatsApp) rather than at deploy. No canary/smoke gate catches missing config before traffic hits it.
- **[medium]** (Stability anti-patterns) Two outbound fetches with no timeout in the WhatsApp-inbound webhook
  - _evidence:_ src/app/api/ops/whatsapp-inbound/route.ts:121 (Chatwoot relay) and :168 (replyToRider Graph API) use raw `fetch()` with no AbortController, unlike every other integration which uses fetchWithTimeout. The :168 reply is not even wrapped in try/catch.
  - _impact:_ A stalled Chatwoot or Graph endpoint hangs the inbound webhook function for its full platform limit; Meta retries the inbound delivery, compounding load. replyToRider throwing/hanging can 500 the webhook and stall rider delivery-confirmation processing.
- **[medium]** (Health checks & Observability) Inconsistent logging — critical money paths still use console.error, no trace correlation through fan-out
  - _evidence:_ infra/admin-alerts/notify.ts logs via console.error (not pino); post-payment-fanout.ts:155 and webhook/route.ts:36,53 use console.error; sentry consoleLoggingIntegration only forwards warn/error so these reach Sentry as untyped strings. No requestId/orderId is threaded as a pino childLogger through runPostPaymentFanout — orderId is in the message text only.
  - _impact:_ The structured-logging + redaction benefits of infra/logging/logger.ts are bypassed on exactly the highest-value failure paths (payment webhook, fan-out). Querying 'all failures for order X' or stitching a fan-out failure to its Stripe event is grep-the-string, not field-filter; correlation across the 3 channels is manual.
- **[medium]** (Stability patterns) AI streamText calls have no timeout/abort — only a soft maxDuration
  - _evidence:_ src/app/api/chat/route.ts:67 (and support-chat/route.ts) call streamText({ model: google(...) }) with no abortSignal; only `export const maxDuration = 30`. Gemini latency/stall is unbounded inside that window.
  - _impact:_ A slow Gemini response ties up the function for the full 30s with no graceful early-abort or fallback message; under a Gemini incident every chat request holds a concurrency slot to the platform limit before failing.
- **[low]** (Deployment & Release / Data layer) DB function hardening gaps confirmed live (search_path mutable, anon-executable SECURITY DEFINER)
  - _evidence:_ Live Supabase advisors (project yjjayivwfqjfppawgyaz): ~25 functions flagged function_search_path_mutable (incl. subscription_status_tick, handle_new_user, verify_otp_attempt); handle_new_user, rls_auto_enable, trg_referral_review_queue_alert executable by anon/authenticated; leaked-password protection disabled; dish-photos public bucket allows listing.
  - _impact:_ Mutable search_path on SECURITY DEFINER functions is a privilege-escalation vector if a same-named object is injected into a role's schema; rls_auto_enable being anon-callable is a latent surface even though it's wired to no trigger. RLS-enabled-no-policy notices are expected (deny-all is the intended protection per the documented model), so those are not risks.

**Strengths:**
- Disciplined timeout layer: infra/http/fetch-with-timeout.ts (AbortController + typed FetchTimeoutError) is injected into the Supabase admin client (15s), ZeptoMail (10s), Zoho (8/10/15s by call type), and Meta WhatsApp (8s) — the documented integration points all have hard ceilings.
- Strong idempotency: Stripe webhook uses webhook_completed_at checkpointing; post-payment-fanout.ts reads per-channel markers (whatsapp_sent_at/email_sent_at/zoho_invoice_id) as a CAS so webhook retries + the hourly cron never double-send; Zoho invoice/payment numbers collision-retry; all internal cron routes gate on INTERNAL_RETRY_SECRET via timingSafeCompare.
- Real bulkheading: service-role admin client vs anon SSR client are cleanly separated (admin-client.ts); fan-out runs the 3 channels with per-channel try/catch + admin WhatsApp alert so one vendor failure never blocks the others; the slow ~70-90s serial Zoho pipeline is deferred off the webhook hot path (handle-stripe-event.ts:703 skipChannels:['zoho']) into the per-minute dispatch cron.
- Deep-ish health check with its own Promise.race timeout (api/health/route.ts), returns 503 + per-check breakdown, and correctly handles Netlify's NEXT_PUBLIC inlining quirk for env presence checks.
- Mature observability wiring: pino with credential redaction + env/service base tags, Sentry log-forwarding that re-redacts before send, Sentry server/client/edge configs with tracing, profiling, replay-on-error, AI-SDK span integration, and a single web-vitals sink.
- Bounded queries throughout the repos: count/head selects, explicit .limit(), .eq on PKs, .maybeSingle(); getCrossDormRecent overfetches a fixed 60 then dedupes — no unbounded SELECT * list scans.
- Region allowlists for Zoho and ZeptoMail validated at module load (prevents sending OAuth tokens to an attacker-controlled host via a bad REGION suffix); next.config.ts image remotePatterns locked to one Supabase host.
