1What this document is

A single source you can read end-to-end to understand how Dormers works as a product — without grepping the codebase or asking the engineer.

This document is written for anyone who needs to understand the system: a new collaborator, a stakeholder reviewing the customer experience, a support agent learning what to expect when a customer says "my plan paused itself."

The diagrams use the names you'd see in the dashboard — "Tonight's dish", "Skip my meal", "Pick a plan" — not the internal variable names. Where the technical name actually matters (e.g. for the engineering team to implement against), Appendix A maps every customer-facing term to the matching code.

How this document stays current

Every section in this PDF was generated from the live source files in src/app/ and supabase/migrations/. The version stamp on the cover is the git short-hash at build time — if you're reading this after newer code has shipped, regenerate the PDF.

2The big picture

Dormers connects three customer-facing things to four behind-the-scenes services. The browser only ever talks to the Dormers app server; the Dormers app server fans the request out to the right service.

The customer never talks to Stripe, Supabase or WhatsApp directly. The Dormers app coordinates everything.

What each piece does

  • Customer's browser — what students see when they visit dormers.ae. Just shows pages and buttons.
  • Dormers app — the brains. Decides what page to show, validates every action, and is the only piece allowed to talk to the other services.
  • Database + login — stores customer profiles, their meal plans, their order history, and handles their email + password.
  • Payments — handles credit-card collection and confirms when money arrives.
  • WhatsApp Business — sends verification codes during signup and (separately) the daily "your meal is on its way" messages from operations.
  • Daily automations — scheduled tasks that run by themselves to keep meal plans up to date, even when no customer is logged in. (See §7.)

4.6 Resetting your password

Three steps, all in-app. No magic-link emails to fish out of spam.

  1. On the Log in page, click "Forgot password?" → enter email → Dormers emails a 6-digit code.
  2. Type the code on screen → Dormers logs you into a temporary recovery session.
  3. Set a new password → done. Stronger-than-default rules enforced.

4.7 Changing your email, password, or WhatsApp number

All three live in the Security & verification card on the Profile page.

  • Change email — type new email; Dormers sends a confirmation link to the new address; the change takes effect when you click it.
  • Change password — type current password (re-auth check), then the new one twice. Forgot path: "Email me a reset link" sends to the email on file.
  • Change & re-verify WhatsApp — type new number → Dormers sends a 6-digit code on WhatsApp → enter code → number is saved as verified.

The "one current + one queued" rule

A customer can hold up to two live plans at the same time:

  • One current plan — the one delivering now (Active, On hold, or Skipped today).
  • One queued plan — bought ahead of time as a renewal, status "Waiting to start".

The dashboard shows the current plan's progress in full. The queued one shows up as a single line above the hero: "Up next: Monthly Premium · starts Mon 27 May". Trying to buy a third plan is blocked at checkout.

Plan #2 was bought as a renewal while Plan #1 was still running. Plan #2's start date sits one delivery day after Plan #1's end date — set automatically at checkout.

How the end date is calculated

The end date isn't just start date + 28 days. It accounts for non-delivery days (Sundays for a 6-day-a-week plan; Saturdays + Sundays for a 5-day-a-week plan), the days the customer has paused, and the days they've skipped (each skip pushes the end out by 1 working day, so they don't lose the meal).

Worked example

Monthly Premium · 6 days a week · starts Mon 29 Apr · 1 skip used → end date is Tue 27 May (24 paid meals × 6-day weeks = 4 weeks of working days, plus the 4 Sundays in between, plus the 1 skip-extension day).

The nine onboarding steps. Religious Mix customers visit step 3; everyone else skips it.

Why "Delivery week" comes before veg days

The veg-day picker on step 3 has to know how many working days there are in the customer's week so it can cap the picker correctly (you can pick at most 4 veg days if your week is 5 days; up to 5 if it's 6). Putting the week-type question first means the picker always knows how many options to offer.

When the dorm is "Other"

The dorm step lists five known dorms plus an Other option. If the customer picks Other, a text input appears, they type the dorm's name, and onboarding completes as usual — they land on the dashboard. But the customer is silently flagged as out of zone:

  • The dashboard shows a banner: "Your dorm is outside our usual delivery radius. Message customer service on WhatsApp so we can confirm whether we can cater to you." with a green "Message us on WhatsApp →" button (canonical wa.me link).
  • The Pick a plan / Renew now CTA is greyed out (cursor: not-allowed). Hovering shows a tooltip: "Outside delivery radius — message us on WhatsApp".
  • If a tampered POST tries to bypass the UI, /api/checkout rejects with HTTP 409 OUT_OF_ZONE.
  • Once delivery feasibility is confirmed, customer service clears the flag manually via Supabase admin (no in-app UI for this).

Server-side checks at the very end

Right before the account is created, the server independently re-checks:

  • Email looks like an email and isn't already taken
  • Password is strong enough
  • WhatsApp was actually verified within the last 30 minutes (UI flag is just a hint)
  • For Religious Mix on a 5-day week: veg days picked are between 1 and 4

If any check fails, the customer sees a friendly error and stays on the same step.

7What runs by itself

Three things happen automatically every day — no human has to push a button. They run on Dubai time so the customer's experience matches their wall clock.

The three daily automations. All times are Dubai local; under the hood they run on the server in UTC.

Why these run at these times

  • Status update at 00:05 Dubai — runs before any deliveries that day, so a plan whose start date is today wakes up Active before 8 PM.
  • Pause counter at 00:10 Dubai — same window. The 5-minute gap between this and Status update is just to keep them from interleaving.
  • Delivery counter at 20:00 Dubai — when most of the kitchen's evening drops have happened. Counts every delivery that wasn't paused or skipped.

Important: the delivery counter is time-based, not delivery-event-based

If a customer's meal didn't actually arrive (kitchen ops issue), the system still marks it delivered at 8 PM. Reconciliation happens out-of-band — operations adjusts manually if a delivery genuinely failed. This is a deliberate trade-off for simplicity.
